## Instructions (Como Usar)

1. Crie este report entre 1 e 4 semanas apos a release, dependendo do ciclo do produto.
2. Colete metricas quantitativas e feedback qualitativo antes de preencher.
3. Envolva PM, engenharia e suporte na coleta de dados — design nao opera sozinho.
4. Use as conclusoes para alimentar o backlog de melhorias e o proximo ciclo de design.
5. Apresente em review de squad ou all-hands para disseminar aprendizados.

> **Dica:** O objetivo nao e julgar se a release foi "boa" ou "ruim", mas entender o impacto real para tomar melhores decisoes no futuro.

## Example (Parcialmente Preenchido)

**Feature:** Novo fluxo de checkout com PIX
**Objetivo:** Reduzir abandono no pagamento de 45% para 30%.
**Resultado:** Abandono caiu para 28% (-17pp). PIX representou 62% dos pagamentos na primeira semana.
**Feedback positivo:** "Muito mais rapido pagar com PIX" (34 mencoes em NPS).
**Issue #1:** QR code expirava sem aviso visual (severity: alta, fix em andamento).
**Learning:** Countdown timer no QR code e essencial — 15% dos usuarios tentaram pagar apos expiracao.
**Proxima acao:** Adicionar timer visual + notificacao push 1 min antes de expirar (P1, designer: Ana, prazo: sprint 24).

## Notes

- Colete dados por tempo suficiente antes de tirar conclusoes — 7 dias e o minimo para features com uso diario.
- Separe correlacao de causalidade — se uma metrica mudou, investigue se foi realmente por causa da release.
- Inclua metricas que pioraram, nao apenas as que melhoraram — transparencia gera confianca.
- Compartilhe o report com todo o squad, nao apenas design — os aprendizados sao coletivos.
- Use os learnings para atualizar frameworks e checklists do time.
- Decision logs evitam re-discussao — registre o racional, nao apenas a decisao.
