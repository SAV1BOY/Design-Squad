# Problem Framing

## Context

Frases prontas para articular e enquadrar problemas de design de forma clara e
acionável. Um problema bem enquadrado é metade da solução — define escopo, comunica
urgência e alinha o time na mesma direção. Estas frases ajudam a evitar o viés de
pular direto para soluções antes de entender o problema.

**Aplicação:** Discovery, sprint planning, design briefs, kickoffs de projeto
**Tom:** Evidence-Driven + User Advocate

## Phrases

### Definindo o problema
- "O problema que estamos resolvendo é: [usuário] precisa [necessidade] mas [barreira]."
- "Hoje, o usuário precisa de [N] passos para [tarefa]. O benchmark do setor é [N]."
- "Os dados mostram que [métrica] está em [valor], quando o target é [valor esperado]."
- "O principal ponto de fricção identificado é [área] — responsável por [X]% dos tickets de suporte."
- "Esse problema afeta [N] usuários por [período], resultando em [impacto mensurável]."

### Enquadrando com How Might We
- "Como poderíamos facilitar [tarefa] para [persona] sem comprometer [restrição]?"
- "Como poderíamos reduzir [métrica negativa] mantendo [métrica positiva]?"
- "Como poderíamos tornar [experiência] acessível para [público excluído]?"
- "Como poderíamos simplificar [fluxo] sem perder [funcionalidade essencial]?"
- "Como poderíamos antecipar [necessidade do usuário] antes que ele perceba?"

### Delimitando escopo
- "Este projeto foca em [escopo]. Explicitamente fora de escopo: [lista]."
- "A restrição principal é [tempo/tech/recurso]. Dentro dessa restrição, o melhor que podemos fazer é [proposta]."
- "Para o MVP, priorizamos [critério]. As features cortadas entram no backlog com tag [label]."
- "O escopo do sprint cobre o happy path. Edge cases e error states entram na sprint seguinte."

### Questionando pressupostos
- "Estamos assumindo que [pressuposto]. Temos dados que confirmam isso?"
- "Essa solução resolve o problema do usuário ou o problema interno?"
- "Se fizéssemos nada, o que aconteceria? Qual o custo da inação?"
- "Qual é a pergunta certa a fazer aqui? Estamos resolvendo o problema certo?"

### Conectando ao negócio
- "Esse problema de UX se traduz em [impacto no negócio]: [métrica] = [valor em R$]."
- "Cada [unidade de fricção] custa [valor] em suporte/churn/conversão perdida."
- "Resolver isso impacta diretamente [OKR/KPI]: [nome da métrica]."

## Variations

### Para stakeholders não-técnicos
- Substituir "UX friction" por "dificuldade que o cliente encontra"
- Substituir "bounce rate" por "pessoas que desistem antes de terminar"
- Substituir "task completion rate" por "quantas pessoas conseguem completar"

### Para comunicação escrita (docs, emails)
- Usar formato "Problema → Evidência → Impacto → Proposta"
- Incluir números específicos em vez de adjetivos ("43%" ao invés de "muitos")
- Referenciar fonte dos dados entre parênteses

### Para comunicação verbal (reuniões, presentations)
- Começar com a história do usuário antes dos números
- Usar uma frase de abertura que gere interesse: "Sabiam que [dado surpreendente]?"
- Fechar com a pergunta que o time precisa responder

## When to Use

- Kickoff de novos projetos e features
- Sprint planning para priorização de backlog
- Design briefs e documents de escopo
- Apresentações para stakeholders justificando investimento
- Sessões de discovery e problem definition
- Retrospectivas para enquadrar problemas de processo
